## 1. async/await 的执行模型（🟡）

**题目**：`await` 会不会创建线程？`await` 之后的代码一定回到原来的线程吗？

**我的答法**：
> await 的核心是切换线程和创建线程没有关系 / 不一定，有上下文时续体由上下文决定，没有上下文时续体由线程池接管

**追问**：ASP.NET Core 里 `.Result` 会不会死锁？库方法里用 `ConfigureAwait(false)` 调用方会感知到什么？

**我的答法**：
> 不会锁死，区别在于有没有上下文 / 界面不会卡顿

**修正**

- ❌「await 是切换线程」→ ✅ **await 是"让出"**：挂起状态机 + 注册续体 + 把线程还回去，**不承诺切换**。Task 已完成时直接同步往下走。
- ✅ 是否回原线程：有 `SynchronizationContext` 就回（UI / 老 ASP.NET），没有就走 `TaskScheduler.Current`（通常线程池）。
- ❌「界面不会卡顿」→ `ConfigureAwait(false)` 只表示"续体不回原上下文"，与 UI 卡顿无关；UI 卡顿的根因是**在 UI 线程同步阻塞**。它只影响它所在的那一个 await。

**正确版（面试口述）**

> `await` 不创建线程，它把当前线程还回去；续体去哪取决于有没有 `SynchronizationContext`。老 ASP.NET 有上下文，`.Result` 会**死锁**（续体回不来）；ASP.NET Core 没有上下文，所以是**线程池饥饿**——不会死锁，但吞吐塌方。`ConfigureAwait(false)` 只是声明"别回原上下文"，少一次 Post，也避免库代码回流导致死锁。

**关联**：[]() §五 5.2 / 5.6、附录 B Q7~Q9

## 2. EF Core N+1（🔴）

**题目**：单次请求打 80 条 SQL，QPS 上不去。① 不改代码怎么确认 N+1？② 三种修法各自适用？

**我的答法**：不会

**正确版**

确认（三个层次）：

1. **日志（改配置不改代码）**：`"Logging:LogLevel:Microsoft.EntityFrameworkCore.Database.Command": "Information"`，看 SQL 条数。
2. **DB 侧**：`performance_schema.events_statements_summary_by_digest` —— 同一 SQL 模板、不同参数、执行次数 ≈ 返回行数。
3. **APM**：单个 trace 里 DB 子 span 数量异常。

判据：**SQL 条数随返回行数线性增长 = N+1**。

修法取舍：

| 修法 | 适合 | 代价 |
| --- | --- | --- |
| `Include/ThenInclude` | 一对一、少量一对多 | 多集合会笛卡尔积 |
| **投影 `Select(dto)`** | 只读列表（最优） | 丢实体完整性 |
| `AsSplitQuery` | 多集合 + 数据量大 | 多次往返，无跨查询快照 |
| 两次查询 + 内存拼装 | 跨库 / 子表巨大 | 代码多一点 |

> 投影最优的原因：**不是"少打几次库"，是"从根上不需要那些数据"** —— 列最少、行数不膨胀、无跟踪开销。

## 3. MySQL 索引设计（🟢）

**题目**：`WHERE user_id=? AND status IN (1,2) ORDER BY created_at DESC LIMIT 20`

**我的答法**：
> user_id 与 created_at 的组合索引

**补强点**

- 理由要讲全：`user_id` 等值锁定前缀 → 同 user 内按 `created_at` 有序 → **反向扫描**，`LIMIT 20` 提前终止、无 filesort；`status` 走 ICP 过滤。
- **为什么 status 不能放中间**：`(user_id, status, created_at)` 下同一 user 先按 status 分段，`IN (1,2)` 要合并两个有序区间 → 退化成 filesort。唯一例外：status 过滤性极强时，用 filesort 换扫描量。
- 「还慢怎么办」顺序：`EXPLAIN` 查是否真用了新索引 → 数据倾斜（大卖家一个 user 几十万单）→ 回表/宽行/冷数据 → 分区归档 + 首屏缓存。

**关联**：[]() §二 Q7、§五 Q25

## 4. 缓存与 DB 一致性（🟡）

**题目**：DB 更新后缓存怎么处理？残余不一致怎么兜？

**我的答法**：
> 1. DB 更新后删除缓存，再次读取时回种 2. DB 更新后更新缓存，同时加速很短的过期时间

**修正**

- ① 对（Cache Aside），但必须能说出**为什么删不更新**：并发写顺序不可控 → 缓存长期脏；计算型缓存重算浪费；删除幂等可重试。
- ② 答成了"另一种方案"。「更新缓存 + 短 TTL」本身**更容易脏**，只在写多读少且写方知道最终值时用，要配版本号。

**残余窗口（要能画出来）**

```text
R 未命中 → 读 DB 拿到旧值
W 更新 DB → 删除缓存
R 把旧值回填   ← 缓存长期是旧值
```

**兜底（按可靠性）**：binlog 订阅（Canal/Debezium，最推荐）> 删除失败重试表 > 延迟双删（sleep 难定）> TTL（最后一道保险，必须有）。

**关联**：[]() §四 Q18、附录 D 图 1~2

## 5. Redis 分布式锁（🔴）

**题目**：① 加锁命令 ② 解锁为什么用 Lua ③ 超过租期怎么办

**我的答法**：
> 加锁用 set key nx

**正确版（三件套）**

```bash
SET lock:order:123 "uuid" NX PX 30000     # NX + 过期 + 唯一 value
```

- 必须一条命令：`SETNX` + `EXPIRE` 两步之间崩溃 → 锁永不过期（死锁）。
- 唯一 value：释放时判断"是不是我的锁"，否则误删别人的。

解锁用 Lua：`GET == value` 之后 `DEL` 必须原子，否则"判断通过 → 锁过期 → 删了别人的锁"。

超过租期：锁自动过期 → 两个持有者同时进临界区。处理：

1. **看门狗**（Redisson 30s 租期 / 10s 续期）—— 线程活着就不断续。
2. **fencing token**（单调递增，存储层校验）—— 唯一能真正兜住的手段。
3. 业务幂等 + 锁持有时间告警。
4. 主从切换丢锁 → `WAIT 1 100` 或换 etcd。

**关联**：[]() §六 Q23~Q27、附录 D 图 3

## 6. MQ 幂等与重放（🟡）

**题目**：① 消息可能重复，怎么保证不重复扣 ② 消费到一半崩了会怎样

**我的答法**：
> 1. 幂等校验，最简单的是入参的 md5 2. 重新消费之前的扣库存消息

**修正**

- ❌ `md5(入参)`：能挡住"同一条消息重投"，但**用户真的下了两单相同商品**时入参相同 → 第二单被误判为重复 → **少卖**。若入参含重新生成的 traceId/时间戳，还会失效。
- ✅ 正确：**业务唯一键**（`order_no`/`biz_no`）+ 唯一索引兜底；没有业务键时用上游幂等 token 或 `(topic, partition, offset)`。
- ❌ 因果讲反：不是"重新消费所以幂等"，而是"**重放是 at-least-once 的必然，所以必须幂等**"。

**重放起点**

| 提交时机 | 崩溃后果 |
| --- | --- |
| 先提交 offset 后处理 | **丢消息**（少扣） |
| 先处理后提交 offset | 重放（重复扣，靠幂等）✅ |

**关联**：[]() §二 Q8、§八 Q32

## 7. P99 长尾排查（🟡）

**题目**：平均 60ms、P99 500ms，CPU 与 DB 正常，怎么查？

**我的答法**：
> 先从服务的线程池排查

**修正**：线程池是头号嫌疑，但直接跳进去会漏掉更便宜的信息。「均值正常、P99 高」= **少数请求被偶发因素拖慢**，先分层。

| 步骤 | 看什么 |
| --- | --- |
| ① 现象分层 | 单接口/全站？集中在时段、版本、机房、用户群？ |
| ② 链路 trace | 500ms 的请求慢在哪一跳 |
| ③ 应用侧 | 线程池队列长度与排队、GC Gen2/LOH 暂停、连接池等待、锁竞争 |
| ④ 系统侧 | CPU `steal`、磁盘 `await`、网络重传 |
| ⑤ 依赖侧 | DB 慢查询/锁等待、下游超时、**重试放大** |

工具：`dotnet-counters` 的 `threadpool-queue-length` / `threadpool-thread-count` / `monitor-lock-contention-count` / `gen-2-gc-count`。

**关联**：[]() §七 Q22

## 8. 秒杀设计（🟢）

**题目**：1000 QPS、100 件库存、不能超卖。

**我的答法**：
> Redis + Kafka + mysql；Redis 预扣减，成功信息存 Redis list → 写 Kafka → 消费落库用乐观锁（库存 >= 购买量）

**补强点**

- **Lua 原子**：幂等判断 + 库存判断 + `DECRBY` + `LPUSH outbox` 必须一个脚本。
- **outbox 不能取出来就删**：`RPOPLPUSH` 到 processing，投递成功后删（崩溃可恢复）。
- ❌「乐观锁」→ ✅ **条件更新** `UPDATE ... SET stock = stock - ? WHERE id = ? AND stock >= ?`，看影响行数；高冲突下不重试。
- **唯一索引**兜住重复消费；扣库存 + 订单 + 流水同一事务、批量提交。
- **降级**（分水岭）：Redis 挂了 → 限流 + DB 条件更新直扣，**宁可少卖不可超卖**；预扣数据以 DB 为准对账。
- **少卖**：预扣成功落库失败 → 补偿回滚 + 对账。

**关联**：[../seckill-1000qps.md](../seckill-1000qps.md)、[]() §四

## 9. CAP（🔴）

**题目**：Redis 主从 + MySQL 半同步 + Kafka `acks=all`，你们是 CP 还是 AP？C 指什么？

**我的答法**：不会

**正确版**

- **C = 线性一致**：看起来像在单机上按某个全局顺序执行，读到的永远是最新已提交值（不是"最终一致"，也不是 ACID 的 C）。
- **A**：非故障节点在有限时间内返回**非错误**响应（允许旧值）。
- **不能选 CA**：分区不可避免，P 不是选项。
- 我们的答法：**整体 AP，关键路径局部 CP**。
  - Redis 主从 = AP；MySQL 半同步 = 偏 CP；Kafka `acks=all+min.insync` = 偏 CP；库存单行条件更新 = 局部 CP。
- 加分：PACELC —— 无分区时在**延迟 L** 与一致性 C 之间选，跨地域同步复制至少加一个 RTT。

**关联**：[]() §一~§三

## 10. 订单 30 分钟未支付自动关闭（🟡）

**题目**：① 两种实现与取舍 ② 多实例重复关闭怎么办 ③ 时钟影响

**我的答法**：
> 1. 定点轮询数据库、RabbitMQ 死信队列 2. 同一个订单幂等校验 3. 不会影响

**修正**

- ① 两方案对；再加第三种 **Redis ZSet**（`score=到期时间戳`，`ZRANGEBYSCORE now`）。生产常见 **MQ/Redis 触发 + 扫表兜底**（延迟消息会丢，扫描不会漏）。
- ② 幂等要落到**条件更新**：`UPDATE t_order SET status=CLOSED WHERE id=? AND status=WAIT_PAY`，**影响行数为 1 才算成功**；关闭订单与释放库存同一事务，库存流水按 `order_no` 唯一。
- ③ ❌「不会影响」→ **影响很大**：应用侧算 `now + 30min` 会因时钟漂移早关/晚关；MQ TTL 由 **broker 时钟**决定；多实例 `now` 不一致 → 一台认到期、另一台不认。做法：以**数据库时间**为准、存**绝对到期时间戳**、NTP + 漂移监控、阈值留缓冲。

**关联**：[]() §三 Q17、[]() §二 Q10

## 三条共性缺口（下一轮重点）

1. **只有方案名，没有"为什么/代价"** —— md5、乐观锁、时间戳都说得出名字，但说不出失效场景。
2. **缺兜底与边界** —— 降级、对账、幂等落地、少卖/漏单，这才是"用过"和"懂"的分界线。
3. **排查类缺方法论** —— 习惯直接猜组件，而不是先缩小范围。
